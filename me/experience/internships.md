# 实习

- 2026.04—08，哔哩哔哩：AI 产品经理实习生，在「花生」团队。实际干的横跨研发预研、数据分析和产品调研：搭 Demo、研究视频草稿结构、做 BI 报表、参与成本治理。

## 网易云音乐

第一份实习在网易云音乐，做 AI 音乐方向。我投了好几家，网易云给了面试，过了，运气成分不小。我有绝对音感，做过 [DAW](https://github.com/shenxianovo/DAW)，在漫协上过台，这些可能有点帮助，说不准。

做下来的感受是，AI 音乐受版权限制，能做的事有限。相比之下，我觉得 AI 生图、生视频更值得做。

## 找暑期实习：技术岗没走通

2026 年春天，我一边在网易云实习，一边找暑期实习。一开始还是投了一堆技术岗，这些面试都要现场手撕算法，我全挂了。我没打算不做技术，只是技术岗招聘这条路当时确实走不通。

那时 Opus 4.6 出来，我已经用了一两个月，AI 辅助开发能做到什么程度，我体会得很直接。我甚至觉得以后很多技术岗的活，靠跟 AI 协作就能干完，可行业挑工程师的办法还没变，想入行还得先过手撕算法。

于是我转投非技术岗。投了几个，正好被 B 站捞进面试。这其实是日常实习，不是原来想找的暑期实习。2026 年 4 月 1 日一面是产品 Leader 面的，面完直接就过了。我还是觉得运气挺大。

## 哔哩哔哩「花生」

岗位叫 AI 产品经理实习生，在 AI 剪辑 Agent「花生」团队。当时的 JD 里有句话挺特别：「我们不会区分你是产品还是研发，我们都叫 Agent 工程师」，职责里也一直强调对前沿 AI 敏感、自己动手搭 Demo、解决真实问题。我没早早打算当产品经理，是技术岗面试不顺，正好碰上了这个机会，而这个岗位刚好适合写过代码、又爱折腾 AI 的人。

进去以后发现，这话还真不是说说而已。总结一下，我在花生干的活大概是：半个研发（预研、做 Demo），半个数分（搭 BI 报表），半个产品（调研）。头衔是 AI 产品经理，干的活没按传统岗位分得那么清。

先说预研。花生是个 Agent，用户用自然语言说想要什么，它帮忙做视频、剪视频。当时视频草稿是 JSON 结构，要加轨道、动效、转场、嵌套内容都很别扭。我一开始改现成的 MG 动画 Demo，越改越觉得它缺一个统一的结构，再加功能只能不停打补丁。于是自己做了 MGFlow，把创意、脚本、分镜、视觉设计、动效一直到渲染整个走了一遍；又做了 AIR，试着用一套 Block/DAG 结构表达 Chat、Canvas 这些不同的视图，另外还做了个测试和比较模型效果的画布。这些原型很多不是为了交付功能，是用来帮我想清楚问题出在哪。

做了几轮 Demo，我发现不一定非得给 AI 视频创作再发明一套 DSL。后来看了 Remotion，又在社区里找到 HyperFrames：它把视频当成一张带时间轴的网页，草稿用 HTML 写，Agent 改代码和人在编辑器里拖拽，改的是同一份东西。我研究、验证了这个思路，做了 MG 动效叠加、文字 PV 之类的演示，在团队里讲了它跟原来 JSON 草稿各自的取舍。后来团队采用了这个方向，由技术同事接着开发。我还看了新版 Planner 的 Agent SKILL 规范，试着用动画 Pattern 和模板让模型直接生成的动效好看一些。整个过程一边写代码验证，一边读开源项目、讨论方案，说不清算研发还是算产品。

另一块是数据分析和成本治理。起因是排查用户问题时，我在异常 Trace 和积分消耗里看到一些用量不太对劲，值得查一查。我拉了连续三天的全量数据交叉核对，然后把这次一次性的分析做成了团队能用的 T+1 BI 报表，按用户类型、底层模型能力这些维度看积分消耗，给之后做风控、调免费额度、压模型成本当依据。这一块又更像数据分析师，跟写需求的产品经理不太一样。

要说实习里有没有谁特别影响我，具体的同事或 Mentor 我想不出来，倒是花生这个团队让我印象很深。团队自己也在试 AI Native 的干法，JD 里说的「不分产品和研发」，平时确实是这样。

AI Native 有些很具体的做法。产品侧每个人每月都有 AI 额度，走公司内部的模型服务，按 API 用量计费。这是用模型的额度，不是发到手里的钱。原来的额度我根本不够用，后来自己申请提高了。我一直在追最新的模型，主力从 Opus 4.6、4.7、4.8 一路换到后来的 Fable 5，新的一出来就想试，试完也是真拿来做日常的预研和开发。

我自己买了每月 100 美元的 Codex Pro，有次看用量记录，最近 30 天的消耗按 API 价格折算居然要 2139 美元。两种算法差太多了，重度用的话，按 API 价算出来的数字很吓人，所以我觉得直接拿 API 价格给员工定用量预算不太合理。

那边信息怎么流动我也记得。每周周会，部门老板会讲他这一周对业务和 AI 的想法。我的工位离老板、技术 Leader、产品 Leader 都很近，产品 Leader 就坐我身后。他们平时直接在那儿讨论工作，我也能加进去。我能自己用 AI 做原型，也能直接听到团队在琢磨什么，参与业务和技术上的讨论。

这段经历没让我想去做产品。我反倒发现，围绕一个 AI 产品解决问题时，做原型、懂技术、判断方案、看数据，不一定非得分给几个互不相干的岗位。

后来离开 B 站去字节，主要是我想 build some stuff，喜欢自己动手把一个想法做成能跑的程序或系统。花生让我碰了产品、预研和数据分析，但我还是想回研发。于是接着找工程方向的机会，2026 年 8 月进了字节。

## 字节跳动 ModelHub

到了字节 ModelHub 团队，业务又多又复杂。跟前两段实习比，光把业务和现有系统摸清楚就够费劲的。

我摸系统的办法跟「先把代码通读一遍」不太一样：代码我基本不自己读，看代码库、理解代码主要交给 AI Agent。我自己盯的是业务和工程环境里的关键信息：业务逻辑是什么，涉及哪些仓库，各服务的 PSM，部署在哪些区域，依赖哪些基础设施，怎么发版，怎么测试。先把这些让业务跑起来的东西摸清，代码层面的定位和修改再交给 AI。进一个复杂系统，我实际就是这么干的。

代码主要靠 Agent 读和改，我就越来越觉得，AI 时代 CI 和自动化验证太重要了。Agent 生成、修改代码很快，验证要是跟不上，交付速度和可靠性最后还是被老流程卡住。

最近看到 [SpaceX AI 的 Lauren Tan（poteto）](https://x.com/poteto)分享一个月交了 2500 多个 PR 的 Agent 工作流，也在关注 [yetone 做的 Magpie](https://github.com/yetone/magpie)，还有他演示的纯 AI 工作流开发。说实话有点羡慕。我羡慕的倒不是 PR 数量或者写代码快，是他们有足够的自主权，可以按自己的想法改整个研发流程。光用 AI 提高我一个人的效率不够，我更想让协作、验证和交付的方式也跟着模型能力一起变。

以后是进一个本来就有这种自主权的团队，还是自己去推动研发流程的变化，我还没想好。在漫协当社长时，我确实推过一些改变：整理交接资料，建文档库和网站，想让经验别只留在某个人脑子里。但我没因此就决定以后要专门去推动组织变革。要是能直接进一个已经有足够自主权、允许大家改进做事方式的团队，那最好。
